# Edge Node agent guide

This is the root operating contract for coding agents in `edge_node`. Keep it limited to stable,
repository-specific rules. Read the code and the nearest relevant README or `AGENTS.md`; nearer
instructions override this file.

## Core context

`edge_node` packages the Ratio1 node runtime and owns repository-local extensions, plugins, commands,
and deployment surfaces. Two important dependencies are maintained as separate repositories and
installed as Python packages:

- `naeural_core` owns the runtime engine and base plugin contracts.
- `ratio1_sdk` provides the `ratio1` package and client/workload APIs.

Local `naeural_core/` and `ratio1_sdk/` directories are independent repository checkouts, not Edge
source. Follow their own instructions, test and commit there separately, and never include them in an
Edge commit.

`device.py` is a deliberately thin entrypoint. Treat it as frozen unless the task explicitly requires
startup behavior and the change cannot live in `constants.py`, an extension, or an upstream project.
Production behavior normally belongs under `extensions/`; `plugins/` is primarily tutorial/example
code unless a production path imports it.

Development is container-first. The repository is mounted at `/edge_node`, and host Python may lack
runtime dependencies. `.devcontainer/Dockerfile` uses the repository's Python 3.13 development base.

## Working loop

1. Inspect `git status --short --branch`, the current branch, and the relevant diff. Preserve unrelated
   user changes and local-only checkouts.
2. Read the nearest instructions, implementation, tests, and the smallest relevant README.
3. Reduce the task to first principles: actual outcome, constraints, invariants, unknowns, and a
   verifiable success condition. Test inherited assumptions against code and runtime evidence.
4. Reproduce or inspect real behavior before diagnosing. Treat old notes and commit messages as clues,
   not proof.
5. Make the smallest coherent change. Do not add speculative abstractions or clean up adjacent code.
6. Run the narrowest useful check first, then broaden in proportion to risk.
7. Critique the weakest assumption, regression surface, security impact, operability, and rollback.
8. Hand off the outcome, exact changed files, observed checks, baseline or skipped failures, and risks.

## Routing exceptions

- Devcontainer work: read `.devcontainer/README.md`, the selected `devcontainer.json`, and
  `.devcontainer/Dockerfile`. Rebuild and verify Python/imports inside the resulting container.
- RedMesh backend work: first read `extensions/business/cybersec/red_mesh/AGENTS.md` and use its tests.
- Upstream behavior: change `naeural_core` or `ratio1_sdk` in their own repositories rather than hiding
  the requirement in an Edge compatibility shim; add Edge integration evidence when needed.
- Operator surfaces (`cmds/`, Docker/Compose, and `.github/workflows/`) require explicit impact and
  rollback review. Active workflows may publish images or tags.

For every other subsystem, use its nearest README, implementation, and matching test directory rather
than expanding this root file with a catalog that will become stale.

## Verification

Use the intended devcontainer/runtime container when host imports or test tooling are unavailable. Do
not install persistent host dependencies merely to make a check runnable. Record the container/image,
Python version, and relevant device assumptions for environment-sensitive work.

Common patterns:

```bash
python3 -m py_compile path/to/changed.py
python3 -m unittest discover -s path/to/tests -p 'test_*.py'
devcontainer build --workspace-folder .
```

- Match checks to the changed contract; a broad green suite can still miss the requested behavior.
- Add a focused regression test for a bug when practical.
- Inspect output for skipped work, handled errors, and fallback paths instead of trusting exit status
  alone.
- If a broad suite is baseline-red, report the exact failure and prove the changed concern narrowly.
  Never weaken tests or production behavior to obtain green output.
- After devcontainer changes, verify `python3 --version` and required imports in the rebuilt image. An
  existing container does not prove a new image builds.

## Implementation and safety boundaries

- Prefer repository-local extension points without duplicating upstream runtime or SDK behavior.
- Keep validation at API, storage, security, and other external boundaries.
- Match existing two-space Python style, `CONFIG` merge patterns, module `__VER__` conventions, and
  plugin logging such as `self.P(...)` where present.
- Never log or commit populated `.env` files, node keys, wallet material, authorization documents,
  tokens, credentials, customer targets, or `_local_cache` data.
- `_local_cache/`, generated bytecode, model data, logs, and local dependency checkouts are runtime or
  local state, not source.
- Live scans, deployments, blockchain writes, whitelist changes, `cmds/reset_*`, purge/delete actions,
  and container or volume removal require explicit scope and exact targets. Inspect first and prefer
  dry-run or preview paths.
- Do not modify `device.py`, active CI, publishing paths, or shared auth/security contracts as a
  drive-by fix.

## Git discipline

- Work on the branch named by the user or task. Do not switch, rebase, merge, push, or open a PR unless
  the current workflow authorizes it.
- Create every new branch from an up-to-date `develop`; never branch from `main`.
- Never push directly to `develop` unless the user explicitly requests that push in the current task.
- Never push to `main`.
- Preserve dirty state and stage exact paths; never use `git add -A` in a mixed worktree.
- Never commit dependency checkouts, caches, runtime data, generated files, secrets, or unrelated user
  changes.
- Use a focused Conventional Commit summary. For non-trivial commits, include what changed, why,
  verification, and known limitations in the body.
- Never rewrite pushed/shared history or force-push without explicit approval.
- Before handoff, run `git diff --check`, inspect the staged diff, and report anything intentionally
  left uncommitted.

## Durable context and completion

- Keep this file free of task progress, dated implementation history, role cards, and memory logs.
- Put subsystem truths in the nearest README or `AGENTS.md`; prefer executable checks over reminders.
- For long work, maintain a concise task/plan artifact with scope, decisions, progress, validation, and
  restart instructions.
- A change is complete only when the requested scope is delivered, the diff is clean and intentional,
  relevant checks pass or are honestly bounded, failure modes were reviewed, and the handoff states
  remaining risks.
