# localnet

An isolated copy of the Ratio1 mainnet infrastructure on one machine, built from real node processes. It
exists to reproduce production problems of the oracles (chain store, dAuth, R1FS, Deeploy) and to measure
a code change against the code it replaces, under the same load, without deploying anything.

Nothing in a localnet can reach a public network, and no production key, credential or record is used.

## What runs

| Part | On mainnet | In a localnet |
|---|---|---|
| Brokers | 4 EMQX 5.8.7 brokers joined by 12 MQTT bridges | the same 4 brokers, configured by the code that renders the mainnet brokers (`r1infra` in `ratio1-cyber-infra`), same session and file-descriptor limits |
| IPFS relays | 2 Kubo relays in a private swarm, each behind nginx (TLS 1.3, basic auth, 3 endpoints) | the same, with the Kubo binary of the node image and a fresh swarm key |
| Oracles | 11, of which 4 are the seeds next to the brokers | 11 real node processes by default. The 4 seeds run every plugin. The others run "headless": the whole node except its web plugins (see below) |
| Other nodes | about 216 | 2 real workers, and 216 emulated nodes with real keys that send signed heartbeats and ask dAuth for their settings |
| Revoked nodes | a list every dAuth oracle carries; most dAuth requests come from nodes on it | 40 emulated nodes on that list, retrying on the node's own schedule |
| Blockchain | Base, through a public RPC | a local JSON-RPC service that answers the contract calls from a state file, with a configurable delay |
| Public names | `dauth.ratio1.ai`, `deeploy-api.ratio1.ai` and others, through Cloudflare tunnels shared by the oracles | `dauth.localnet`, `deeploy-api.localnet` and others, through one nginx that spreads requests over the oracles |
| Node code | the image | three source trees (SDK, core, edge_node) mounted over the image, so two versions can be compared |

Nodes run the production entry point with the production configuration files. A seed gets its settings
from its environment and every other node from dAuth at start, as on mainnet. The network name is
`mainnet`, so mainnet-only code paths and constants are in effect (24-hour epochs, the mandatory revoked
list); only the addresses of services are replaced.

### What differs from mainnet

- **Headless oracles.** Each web plugin of a node is two processes of about 650 MB, so a full oracle
  takes about 5.4 GB. A headless oracle (about 0.6 GB) takes part in messaging, the network monitor, the
  chain store and oracle sync, and is registered on the chain, but serves no HTTP requests. Raise
  `--full-oracles` on a machine with more memory.
- **One host.** All nodes share one machine's CPU and disk. CPU pools keep the brokers and load
  generators off the CPUs of the nodes (`--infra-cpus`, `--node-cpus`). The node's own low-memory restart
  is switched off, because it reads the host's memory.
- **The chain** answers at once apart from the configured delay, and accepts every transaction.
- **Emulated nodes** send heartbeats and dAuth requests only. They run no jobs.
- **State is synthetic.** The chain store of every oracle starts with 3,657 made-up records (about
  5.5 MB, the size on mainnet) and 30 old-style job pointers whose documents exist nowhere.
- **Seeds start with the complete list of allowed senders**, as a long-running mainnet seed does. A seed
  fills that list from the on-chain oracle list once at start-up and then every 15 minutes, and can only
  name oracles whose heartbeats it has already registered. Seeds that start together for the first time
  therefore keep a partial list (one to four seeds, itself always) for 15 minutes: writes are replicated
  only to that partial list, and a seed that listed only itself gets no write confirmed. `init` writes the
  eleven oracles into each seed's `authorized_addrs`; `init --empty-whitelist` keeps the first-start
  behaviour, for work on that start-up path.
- **No tunnels, no MinIO, no update server.** The update check fails harmlessly.
- **No image registry.** Container apps use images copied in from this machine (`image`); a pull fails.

Read results as comparisons between code versions under the same conditions, not as predictions of
mainnet numbers.

## Safety

- The Docker network is `internal`: it has no route out and resolves no public name.
- Every process started here (`node/launch.py`, the chain service, each load generator) first proves that
  it has no default route, cannot connect to public addresses and cannot resolve public names
  (`node/guard.py`), and exits otherwise.
- The SDK's table of service addresses is replaced before any node code is imported
  (`node/chain_shim.py`). A node refuses to start if a public address is left in it.
- All keys, passwords and certificates are generated by `init` and are throwaway.
- Do not attach a localnet container to another Docker network.
- Nodes in `--docker-nodes` are privileged (as production nodes are). They are acceptable only because
  they sit on the internal network; their inner daemon starts only after the guard passed.

## Requirements

- Docker with Compose v2, Python 3.10+ with PyYAML, `openssl`.
- The node image `ratio1/edge_node_gpu:mainnet` (any image with the node's dependencies works: set
  `R1_LOCALNET_NODE_IMAGE`), `emqx/emqx:5.8.7`, `nginx:1.24`.
- A checkout of `ratio1-cyber-infra` next to this repository, or `R1_INFRA_REPO` pointing at one.
- For the default topology about 30 GB of free memory and 12 CPU threads.
- Optional: a `py-spy` binary in `<home>/tools/py-spy` for the `profile` command.

## Use

```bash
LN="python3 docker-compose/localnet/localnet.py --home /path/to/state"

# 1. Extract the code versions to compare (any git revisions of the three repositories).
$LN stage base --workspace /path/to/workspace --core origin/main --edge origin/develop --sdk origin/main
$LN stage new  --workspace /path/to/workspace --core my-branch   --edge my-branch      --sdk my-branch

# 2. Create and start a localnet on one version.
$LN init --arm base --infra-cpus 0,6 --node-cpus 1-5,7-11
$LN up

# 3. Run an experiment. Results go to <home>/results/<time>_<scenario>_<version>/.
$LN scenario docker-compose/localnet/scenarios/incident.json

# 4. Do the same on the other version and compare the two result folders.
$LN down --purge
$LN init --arm new --infra-cpus 0,6 --node-cpus 1-5,7-11 && $LN up
$LN scenario docker-compose/localnet/scenarios/incident.json
```

`--arm-of NODE=TREE` on `init` gives single nodes another version (mixed fleets). `--startup-of NODE=JSON`
adds production start-up settings to one node only, merged two levels deep into its start-up file, for
example a plugin's debug switch: `r1s-db='{"ADMIN_PIPELINE":{"CHAIN_STORE_BASE":{"CHAIN_STORE_DEBUG":true}}}'`.
The node starts the admin plugins its file names first, in that order, so a plugin added this way starts
earlier unless the plugins before it are listed first with `{}`.

### Container apps

A production node runs its own Docker daemon inside the node container (the image starts it when
`EE_DD=1`, and the container is privileged); container apps run in that daemon, and their fixed-size
volumes are ext4 images on loop devices the node mounts itself. `init --docker-nodes r1w-01,r1w-02`
gives chosen nodes the same: `EE_DD=1`, privileged, a private cgroup namespace, the inner Docker data in
its own volume, still attached to the internal network only and publishing no port. `node/dind.sh` runs
the isolation guard before the daemon starts. The smallest cluster that runs container apps:

```bash
$LN init --arm base --oracles 4 --workers 2 --full-workers 0 --fleet 0 --revoked 1 \
  --docker-nodes r1w-01,r1w-02 --web-plugins DAUTH_MANAGER --web-of r1s-01=DAUTH_MANAGER,DEEPLOY_MANAGER_API
$LN up                                          # about 1.5 minutes, about 5.5 GB of memory
$LN scenario docker-compose/localnet/scenarios/container_sync.json   # loads the app image itself
```

(`--revoked 1`: a mainnet dAuth refuses to start with an empty revoked list.) `--web-plugins` and
`--web-of` keep only some web plugins on full nodes; the front then sends each public name only to the
oracles that run it.

- `image <host image> --tag <name> [nodes]` copies an image of this machine into the inner daemons
  (`docker save` into `docker load`) and proves that an inner container reaches no public address or
  name and that a pull from the public registry fails.
- `load run deeploy -- sync-app --job N --node r1w-01 --role provider --key K` creates one app of a
  container-sync set through the Deeploy API, in the shape the Deeploy web app sends
  (`setup --job-type 53` registers generic jobs first).
- `sync-app ... --secret NAME` also sends the set's secret as `ENV.R1EN_SYNC_SECRET`, selected by the
  top-level `secret_paths` as the web app does. The value is derived from the cluster's private
  `secrets.json` and the name, so scenarios and reports carry only the name; another name gives a wrong
  secret, `malformed` sends 32 x "a". The test app writes the byte count of that variable in its
  environment to `/data/secret_len` at every start (65 or 0, never the value) and puts the set's key in
  its publish metadata, so several sets can share a node.
- `sync <key> <provider> <consumer...>` checks a set: the chain-store record on every oracle, each
  publish's delay to each consumer, refused records, and the file the provider wrote as each consumer
  app reads it. PASS or FAIL. `--refusing NODE[=TEXT]` names a consumer that must refuse the set's
  records: it needs a refusal line for the latest record (holding TEXT), no R1FS fetch line and no
  download folder for any of the set's CIDs, nothing applied, and its file unchanged. `--encryption
  r1fs-set-v1|r1fs-default` also requires the latest record on every holding oracle to carry that format
  tag (the set tag with a 64-hex `mac`, the shared-key tag with none); the report names each publish's
  tag and the record's form, never the `mac` itself.
- `custody <job> --secret NAME [--node N --key K --secret-len N]` reads the job's stored copy and
  deployment plan from R1FS with the default key on an oracle (they must hold only the dAuth placeholder
  at `ENV.R1EN_SYNC_SECRET` and not the secret) and the app's `/data/secret_len`.
- Scenario step `sync_off` (node, job, key) checks a job whose SYNC configuration the node refused (a
  malformed secret by default) on a node that runs only that app: the refusal line once per start of the app
  container and no green line; no store read, refusal, quarantine skip, apply or provider line, and no other
  `[sync]` line than the system-volume set-up; the app running without `R1_SYNC_KEY`, `R1_SYNC_TYPE` or
  `R1EN_SYNC_SECRET` (matched by exact name: every app keeps `R1_SYSTEM_VOLUME`, `R1_VOLUME_SYNC_DIR` and
  `R1_SYNC_REQUEST_FILE`), count 0; nothing received, quarantined or downloaded; the node's saved copy of the
  pipeline still says `SYNC.ENABLED` true. `custody` also reports `SYNC.ENABLED` of the stored documents.
- `scan NAME` searches every node's log and cache folder (logs, plugin data, the apps' mounted volumes,
  downloads, store files) for the secret, its SHA-256 (the archive key), that key's first 16 bytes and
  the record MAC subkey; dAuth's bundle records in the chain store (`DAUTH_JOB_SECRETS`,
  `DAUTH_JOB_SECRET_REVISIONS`) are reported apart. It prints kinds
  and paths only.
- More app workers: `--workers 6 --docker-nodes r1w-01,...,r1w-06` (about 0.7 GB each). Deeploy on two
  seeds: add `--web-of r1s-02=DAUTH_MANAGER,DEEPLOY_MANAGER_API`; `load --tag run run deeploy --
  --api http://172.31.90.52:31302 ...` sends a request to r1s-02 alone (seed n is `172.31.90.5n`), with
  the wallet of the scenarios' `run` steps. `switch` of a seed returns once its dAuth answers.
- `switch <node> <tree> [--kill]` recreates one node on another staged tree with the same identity,
  data and inner Docker data: one step of a rolling update or of a rollback. By default the node is
  stopped the way an update stops it (SIGTERM and the grace period).
- `down` kills each node that runs Docker and detaches the loop devices of its apps' volumes from a
  throwaway privileged container on the internal network; it reports any loop device left.

### Oracle-only secret

`init --oracle-secret NAME` puts a fake oracle-only secret in every seed's environment
(`EE_ORACLE_R1FS_SECRET`, as mainnet seeds get it in their `.env`), derived from the cluster's private
`secrets.json` and the name. The probe of every node records, from inside the node process, whether the
variable is in its `os.environ` (`osec_env`) and a check hash of the value its SDK holds in memory (`osec`;
`n/a` for an SDK without the holder). `osecret NAME` compares those readings with the seeds' value by check
hash and prints PASS when no node keeps the variable, every seed and oracle with the holder holds the
seeds' value, and no worker ever held one. `scan NAME` searches every node for the value itself.

Other commands: `status`, `collect` (measure the last minutes by hand), `profile` (which threads and
functions hold the interpreter lock), `replicas` (records each oracle lacks compared with the others;
`--namespaces A,B` also per hash namespace; the replica file is copied out with `docker cp` and read on the
host, so a node under a CPU limit is not slowed by the reading), `cstats` (the chain store's `CSTORE_STATS`
and `CSTORE_CENSUS` lines of nodes, with the buckets of the Deeploy and dAuth namespaces named, the refusal
labels summed and the resync counters per namespace), `loops` (the longest pause of a node's main loop and
chain-store loop, from its probe; `init --probe-period 1` gives a one-second resolution), `trace` (when every
oracle's saved replica shows a Deeploy request in another oracle's request trace),
`compare <scenario> <version> ...` (runs of one scenario side by side; `--curve` prints one line per
phase for the node a scenario squeezes), `load start|run|stop|logs <generator>`, `ctl` (run a command on
the isolated network), `down [--purge]`.

## Scenarios

| File | What it reproduces |
|---|---|
| `scenarios/incident.json` | A Deeploy operation that cannot finish (its target node is gone), then one oracle short of CPU: the mainnet incident of 2026-11-08 |
| `scenarios/restart.json` | Oracles leaving by SIGTERM, SIGKILL and SIGINT and coming back: whether each stays a replication target and how many records it lacks afterwards |
| `scenarios/pinned_client.json` | A licensed node whose dAuth requests always reach one oracle, and that oracle is saturated (mainnet, 2026-11-10) |
| `scenarios/resource_floor.json` | One oracle given less and less CPU under normal load: where it stops answering in time |
| `scenarios/secret_flood.json` | Secret requests for old-style jobs whose documents cannot be read, and what a starting node sees meanwhile |
| `scenarios/container_sync.json` | One container-sync set: a provider app and a consumer app on two workers, two publishes, then the sync check |
| `scenarios/container_sync_rolling.json` | A set that keeps publishing while its workers move to tree `next` one at a time and back to `old` |
| `scenarios/container_sync_custody.json` | A provider created with a set secret through `secret_paths`: the sync check, the custody check (placeholder in R1FS, the app's count), and the secret scan |
| `scenarios/container_sync_secret.json` | A provider and a consumer both created with a set secret on code that supports it: the sync check with the set's format, custody of both jobs (count 0 in the apps), the secret scan |
| `scenarios/container_sync_secret_fleet.json` | A shared-key set and a set with a secret on six workers, with consumers that must refuse (no, wrong or malformed secret), a kill and start of one consumer, then a rollback of three workers to `old` and their re-upgrade; last, the consumer with the malformed secret must have run with SYNC off (`sync_off`) |
| `scenarios/container_sync_tickcost_lowend.json` | Two weak consumer hosts at 0.35 CPU, one on `old` and one on `next`, each refusing every record of a set with two apps of 1,000 history entries: mean `process` time of their app runners, main-loop rate and CPU over the same 1,200 s, `next` within 10 % of `old` (`ticks`) |
| `scenarios/container_sync_secret_mixed.json` | A set with a secret created through a Deeploy oracle on `old`, with one consumer on `old` that refuses, then moves to `next` |
| `scenarios/container_sync_rolling_lowend.json`, `container_sync_secret_lowend.json` | The rolling scenario and the all-`next` part of the fleet scenario with r1w-02 limited to 0.35 CPU and its consumer apps given 1,000 received-history entries each (step `seed_history`) |
| `scenarios/restart_catchup.json`, `restart_catchup_lowend.json` | Deeploy creates and deletes without pause (`deeploy cycle`) while the headless oracle r1s-db is killed for 12 minutes; per signed namespace, what each oracle lacks from 60 s to 810 s after r1s-db's start, its statistics lines and loop pauses. The second limits r1s-db to 0.35 CPU before its start |
| `scenarios/cap_depth_mixed.json` | Writes over and under the 512 KiB record cap and at 64 and 65 levels of nesting through r1w-01's own CStore API, then an oversize value and a `dl:` key from r1s-02 moved to `old`; what every node holds and its counters for 10 minutes |
| `scenarios/trace_hang.json`, `trace_hang_lowend.json` | A Deeploy create held 45 s in its endpoint by a dAuth call that answers late (`load/slowdauth.py`, pinned for r1s-01 only), with no and with one tracked request just before: when every oracle shows the request in r1s-01's request trace. The second repeats the first start with r1s-01 at 0.35 CPU |

A scenario is a list of steps (start a load, wait, begin a measurement phase, stop or throttle a node,
slow the chain, take a profile). See `lnlib/scenario.py` for the step types.

## Measurements

Each phase of a scenario produces one JSON file. Everything is measured the same way on every code
version:

- per node, from a sampler inside the node (`node/probe.py`): inputs received, handled and dropped per
  plugin, queue depth, plugin loop rate, the calls and mean wall time of each plugin's `process` (the core's
  own timer), CPU time and memory of the node process, and CPU time, throttled time and memory of the whole
  container (node process, web servers, managers) from its control group; the scenario step `ticks` gives,
  between two marks, a node's mean `process` time of its container app runners (the loop that runs the sync
  tick), main-loop rate and CPU, and can bound one node's figures by another's;
- what users saw, from the load generators: chain-store writes confirmed and their latency, replication
  delay to every other serving node, refresh outcomes, dAuth outcomes and latency, Deeploy admission time
  and operation timeline;
- every request through the public names, from the front's access log;
- broker counters, chain call counters, container CPU and memory;
- a few log lines that exist in every version (main loop rate, queue overflow warnings, save times).

## Layout

```
localnet.py        host tool
lnlib/             topology, infrastructure, node settings, metrics, profiler, scenario runner
node/              runs in every node container: launch.py, guard.py, chain_shim.py, probe.py
infra/chain_rpc.py the local blockchain and dApp API
ctl/               one-shot helpers: key generation, broker users, chain-store seeding
load/              load generators: fleet, cstore, dauth, deeploy
scenarios/         experiments
```
