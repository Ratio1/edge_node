# localnet

An isolated copy of the Ratio1 mainnet infrastructure on one machine, built from real node processes. It
exists to reproduce production problems of the oracles (chain store, dAuth, R1FS, Deeploy) and to measure
a code change against the code it replaces, under the same load, without deploying anything.

Nothing in a localnet can reach a public network, and no production key, credential or record is used.

## What runs

| Part | On mainnet | In a localnet |
|---|---|---|
| Brokers | 4 EMQX 5.8.7 brokers joined by 12 MQTT bridges | the same 4 brokers, configured by the code that renders the mainnet brokers (`r1infra` in `ratio1-cyber-infra`), same session and file-descriptor limits |
| IPFS relays | 2 Kubo relays in a private swarm, each behind nginx (TLS 1.3, basic auth, 3 endpoints) | the same, with the Kubo binary of the node image and a fresh swarm key |
| Oracles | 11, of which 4 are the seeds next to the brokers | 11 real node processes by default. The 4 seeds run every plugin. The others run "headless": the whole node except its web plugins (see below) |
| Other nodes | about 216 | 2 real workers, and 216 emulated nodes with real keys that send signed heartbeats and ask dAuth for their settings |
| Revoked nodes | a list every dAuth oracle carries; most dAuth requests come from nodes on it | 40 emulated nodes on that list, retrying on the node's own schedule |
| Blockchain | Base, through a public RPC | a local JSON-RPC service that answers the contract calls from a state file, with a configurable delay |
| Public names | `dauth.ratio1.ai`, `deeploy-api.ratio1.ai` and others, through Cloudflare tunnels shared by the oracles | `dauth.localnet`, `deeploy-api.localnet` and others, through one nginx that spreads requests over the oracles |
| Node code | the image | three source trees (SDK, core, edge_node) mounted over the image, so two versions can be compared |

Nodes run the production entry point with the production configuration files. A seed gets its settings
from its environment and every other node from dAuth at start, as on mainnet. The network name is
`mainnet`, so mainnet-only code paths and constants are in effect (24-hour epochs, the mandatory revoked
list); only the addresses of services are replaced.

### What differs from mainnet

- **Headless oracles.** Each web plugin of a node is two processes of about 650 MB, so a full oracle
  takes about 5.4 GB. A headless oracle (about 0.6 GB) takes part in messaging, the network monitor, the
  chain store and oracle sync, and is registered on the chain, but serves no HTTP requests. Raise
  `--full-oracles` on a machine with more memory.
- **One host.** All nodes share one machine's CPU and disk. CPU pools keep the brokers and load
  generators off the CPUs of the nodes (`--infra-cpus`, `--node-cpus`). The node's own low-memory restart
  is switched off, because it reads the host's memory.
- **The chain** answers at once apart from the configured delay, and accepts every transaction.
- **Emulated nodes** send heartbeats and dAuth requests only. They run no jobs.
- **State is synthetic.** The chain store of every oracle starts with 3,657 made-up records (about
  5.5 MB, the size on mainnet) and 30 old-style job pointers whose documents exist nowhere.
- **Seeds start with the complete list of allowed senders**, as a long-running mainnet seed does. A seed
  fills that list from the on-chain oracle list once at start-up and then every 15 minutes, and can only
  name oracles whose heartbeats it has already registered. Seeds that start together for the first time
  therefore keep a partial list (one to four seeds, itself always) for 15 minutes: writes are replicated
  only to that partial list, and a seed that listed only itself gets no write confirmed. `init` writes the
  eleven oracles into each seed's `authorized_addrs`; `init --empty-whitelist` keeps the first-start
  behaviour, for work on that start-up path.
- **No tunnels, no MinIO, no update server.** The update check fails harmlessly.

Read results as comparisons between code versions under the same conditions, not as predictions of
mainnet numbers.

## Safety

- The Docker network is `internal`: it has no route out and resolves no public name.
- Every process started here (`node/launch.py`, the chain service, each load generator) first proves that
  it has no default route, cannot connect to public addresses and cannot resolve public names
  (`node/guard.py`), and exits otherwise.
- The SDK's table of service addresses is replaced before any node code is imported
  (`node/chain_shim.py`). A node refuses to start if a public address is left in it.
- All keys, passwords and certificates are generated by `init` and are throwaway.
- Do not attach a localnet container to another Docker network.

## Requirements

- Docker with Compose v2, Python 3.10+ with PyYAML, `openssl`.
- The node image `ratio1/edge_node_gpu:mainnet` (any image with the node's dependencies works: set
  `R1_LOCALNET_NODE_IMAGE`), `emqx/emqx:5.8.7`, `nginx:1.24`.
- A checkout of `ratio1-cyber-infra` next to this repository, or `R1_INFRA_REPO` pointing at one.
- For the default topology about 30 GB of free memory and 12 CPU threads.
- Optional: a `py-spy` binary in `<home>/tools/py-spy` for the `profile` command.

## Use

```bash
LN="python3 docker-compose/localnet/localnet.py --home /path/to/state"

# 1. Extract the code versions to compare (any git revisions of the three repositories).
$LN stage base --workspace /path/to/workspace --core origin/main --edge origin/develop --sdk origin/main
$LN stage new  --workspace /path/to/workspace --core my-branch   --edge my-branch      --sdk my-branch

# 2. Create and start a localnet on one version.
$LN init --arm base --infra-cpus 0,6 --node-cpus 1-5,7-11
$LN up

# 3. Run an experiment. Results go to <home>/results/<time>_<scenario>_<version>/.
$LN scenario docker-compose/localnet/scenarios/incident.json

# 4. Do the same on the other version and compare the two result folders.
$LN down --purge
$LN init --arm new --infra-cpus 0,6 --node-cpus 1-5,7-11 && $LN up
$LN scenario docker-compose/localnet/scenarios/incident.json
```

`--arm-of NODE=TREE` on `init` gives single nodes another version (mixed fleets).

Other commands: `status`, `collect` (measure the last minutes by hand), `profile` (which threads and
functions hold the interpreter lock), `replicas` (records each oracle lacks compared with the others),
`compare <scenario> <version> ...` (runs of one scenario side by side; `--curve` prints one line per
phase for the node a scenario squeezes), `load start|run|stop|logs <generator>`, `ctl` (run a command on
the isolated network), `down [--purge]`.

## Scenarios

| File | What it reproduces |
|---|---|
| `scenarios/incident.json` | A Deeploy operation that cannot finish (its target node is gone), then one oracle short of CPU: the mainnet incident of 2026-11-08 |
| `scenarios/restart.json` | Oracles leaving by SIGTERM, SIGKILL and SIGINT and coming back: whether each stays a replication target and how many records it lacks afterwards |
| `scenarios/pinned_client.json` | A licensed node whose dAuth requests always reach one oracle, and that oracle is saturated (mainnet, 2026-11-10) |
| `scenarios/resource_floor.json` | One oracle given less and less CPU under normal load: where it stops answering in time |
| `scenarios/secret_flood.json` | Secret requests for old-style jobs whose documents cannot be read, and what a starting node sees meanwhile |

A scenario is a list of steps (start a load, wait, begin a measurement phase, stop or throttle a node,
slow the chain, take a profile). See `lnlib/scenario.py` for the step types.

## Measurements

Each phase of a scenario produces one JSON file. Everything is measured the same way on every code
version:

- per node, from a sampler inside the node (`node/probe.py`): inputs received, handled and dropped per
  plugin, queue depth, plugin loop rate, CPU time and memory of the node process, and CPU time, throttled
  time and memory of the whole container (node process, web servers, managers) from its control group;
- what users saw, from the load generators: chain-store writes confirmed and their latency, replication
  delay to every other serving node, refresh outcomes, dAuth outcomes and latency, Deeploy admission time
  and operation timeline;
- every request through the public names, from the front's access log;
- broker counters, chain call counters, container CPU and memory;
- a few log lines that exist in every version (main loop rate, queue overflow warnings, save times).

## Layout

```
localnet.py        host tool
lnlib/             topology, infrastructure, node settings, metrics, profiler, scenario runner
node/              runs in every node container: launch.py, guard.py, chain_shim.py, probe.py
infra/chain_rpc.py the local blockchain and dApp API
ctl/               one-shot helpers: key generation, broker users, chain-store seeding
load/              load generators: fleet, cstore, dauth, deeploy
scenarios/         experiments
```
